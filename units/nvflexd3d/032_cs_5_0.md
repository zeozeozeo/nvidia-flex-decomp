# 032 `cs_5_0` — SolveSprings

**Status: blocked (not reconstructed).**

## Interface
- `cbuffer consts` (b0, 26 registers)
- `StructuredBuffer<int> halfSpringOpposites` (t1), `StructuredBuffer<float> halfSpringLengths` (t2),
  `halfSpringStiffness` (t3), `particleSpringBegin` (t4), `particleSpringEnd` (t5),
  `reverseLookup` (t6), `StructuredBuffer<float4> sortedNewPositionsTex` (t7)
- `RWByteAddressBuffer deltas` (u0, `dcl_uav_raw`), `groupshared float3[512]`
- thread group 512x1x1

## Algorithm (recovered, not expressible)
Eight threads cooperate on one body: each walks every 8th spring of the body's range,
accumulating `d * (length - |d|) * (1 / (w0 + w1)) * stiffness` with the sign-corrected
stiffness, block-reduces the eight contributions, and lane 0 accumulates
`float4(sum * pos.w, springCount)` into the body's 16-byte slot of the raw UAV.

## Blocker
The final accumulation is a read-modify-write of the raw UAV
(`ld_raw ... u0.xyzw` at line 89 of `032_cs_5_0.asm`). The vkd3d-shader SM5 front end
declares only `Store`/`Store2` on `RWByteAddressBuffer`; `Load`, `Load2`, `Load4`,
`InterlockedAdd` and `InterlockedCompareExchange` all fail with
`E5005: Method ... is not defined on type 'RWByteAddressBuffer'`.
Reading the previous delta is semantically required (SolveDensities, SolveShapes and
SolveSprings accumulate into the same buffer), so the shader cannot be written without
changing the binding set; it is left unreconstructed rather than approximated.

## Note
The same limitation applies to shader 075 (the other `SolveSprings` variant).
